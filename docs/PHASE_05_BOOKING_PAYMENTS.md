# مرحله ۵ — کنترل رزرو و پایداری پرداخت و پیامک، نسخه 1.12.0

تاریخ: 2026-10-01، Asia/Tehran. مبنا: main پس از PR۴، `16dbccd2d957e993c21057dcc5485ac084acd8fe`. شناسه نهایی PR، commit/tree و آرشیو در گزارش تحویل کنار خروجی‌ها ثبت می‌شوند. این مرحله آماده‌سازی کد است؛ سایت زنده، رزرو production، پرداخت/پیامک واقعی و حساب مدیرکل production تغییر نکردند.

## رفتار رزرو

- مدیرکل در مرکز تنظیمات، بخش نوبت‌دهی، `booking_enabled` و متن فارسی `booking_disabled_message` را تغییر می‌دهد. این دو فیلد در همان تنظیمات نسخه‌دار، تاریخچه، بازیابی و audit موجود قرار دارند؛ تعداد فیلدهای runtime اکنون ۴۵ است. خواندن عمومی فقط کلید و متن را اضافه می‌کند، بدون credential درگاه یا پیامک.
- پیش‌فرض نصب تازه خاموش است. مهاجرت 0017 حتی اگر ENV قدیمی `BOOKING_ENABLED=true` داشته باشد، override خاموش ثبت می‌کند؛ بعداً فقط تغییر آگاهانه مدیرکل آن را روشن می‌کند. این کلید مستقل از sandbox/merchant است؛ منع sandbox در production حفظ شد.
- خاموش بودن، رزرو جدید، ایجاد hold، شروع پرداخت، جابه‌جایی بیمار و عضویت جدید در انتظار را با 409 و پیام قابل ویرایش متوقف می‌کند. چک مجدد داخل قفل SQLite و خواندن تازه، رقابت با تغییر تنظیمات را می‌بندد؛ صرفاً دکمه پنهان نشده است.
- ورود/پروفایل، مشاهده نوبت و پرونده، گفت‌وگو و فرم مراجعه، لغو طبق مهلت قبلی، دیدن و ترک انتظار برقرار می‌مانند. پیشنهاد جدید از لغو نوبت به انتظار صادر نمی‌شود؛ اطلاعات و اعضای قبلی حذف نمی‌شوند. خواندن زمان‌های عمومی هنگام خاموشی 409 می‌دهد.
- سیاست برای رزرو خودکار بیمار است. کارکنان مجاز همچنان عملیات داخلی نوبت‌های موجود را انجام می‌دهند؛ عملیات آن‌ها برای پیگیری پرونده و لغو/بازپرداخت بسته نمی‌شود. offer جدید حتی در لغو توسط کارکنان هم صادر نمی‌شود.
- صفحه اصلی، ناوبری، FAQ و پنل بیمار وضعیت درست و راه تماس را نشان می‌دهند. bootstrap HTML و API از یک سیاست می‌خوانند، no-store است؛ مرورگر روی focus، پیام BroadcastChannel و هر ۳۰ ثانیه تازه می‌شود. بازکردن فرم رزرو هم آخرین وضعیت را می‌گیرد و API مرجع نهایی است. خطای refresh رزرو را در رابط می‌بندد، اطلاعات تماس حفظ می‌شود.

## پرداخت

بازگشت پرداخت شروع‌شده قبل از خاموشی همچنان باز است. تماس verify بیرون تراکنش نوشتن انجام می‌شود؛ سپس `BEGIN IMMEDIATE`، `expire_all` و خواندن دوباره Payment تعیین‌کننده نتیجه است. 100 و 101 فقط همراه رسید معتبر پذیرفته می‌شوند. دو OK هم‌زمان همان نوبت و کد رهگیری را می‌گیرند؛ NOK، خطا/شکست دیررس و worker انقضا نمی‌توانند verified/verified_conflict را خراب کنند. UNIQUE موجود `Appointment.payment_id` حفظ و در migration بررسی شد؛ شکست constraint به بررسی مطب می‌رود، بدون ساخت نوبت تکراری.

hold منقضی فقط وقتی زمان اصلی هنوز آزاد باشد تکمیل می‌شود. ظرفیت پر، بازپرداخت ثبت‌شده، برخورد ref_id یا تعارض constraint نتیجه manual-review دارند. برای ref_id تکراری، constraint شکسته نمی‌شود و رسید حداقلی در raw_response برای رسیدگی محفوظ است. verified_conflict یک نتیجه پایدار است؛ بازپرداخت واقعی خودکار انجام نمی‌شود. نشست/رزرو تازه برای callback لازم نیست و خاموشی رزرو آن را نمی‌بندد.

authority ناشناس شبکه درگاه را فراخوانی نمی‌کند. پاسخ خراب، کد با نوع اشتباه و موفقیت بدون ref_id معتبر، نوبت نمی‌سازند. خطای ارتباط نتیجه نامشخص است؛ پیام رابط می‌گوید دوباره پرداخت نکنید و با مطب بررسی کنید. raw_response جدید فقط code/authority/ref_id دارد؛ PAN، hash کارت و متن خطای ارائه‌دهنده در آن ذخیره یا به بیمار بازتاب داده نمی‌شود. redirect و proxy محیطی برای تماس ثابت HTTPS درگاه غیرفعال‌اند؛ timeout ۱۵ ثانیه باقی است.

مبلغ داخلی تومان است؛ request از `currency=IRT` و verify از همان مبلغ/authority استفاده می‌کند. قرارداد پایه در [مستندات اتصال زرین‌پال](https://www.zarinpal.com/docs/paymentGateway/connectToGateway.html) و [واحد پول](https://www.zarinpal.com/docs/paymentGateway/moreFeatures/currency.html) بررسی شد؛ سایت مستندات SPA است و محتوای chunkهای رسمی خوانده شد. این بررسی، پذیرش پرداخت واقعی نیست. قبل از فعال‌سازی، سناریوهای موفق، لغو، retry/101، رسید و مبلغ واقعی باید در محیط مستقل ارائه‌دهنده پذیرفته شوند.

تغییر حساب یا sandbox از پنل/restore تا تعیین تکلیف وضعیت‌های created/redirected/verification_error مسدود است. ENV و کلید تاریخی درگاه را در حالی که تراکنش قابل بازگشت دارید عوض نکنید؛ پرداخت‌های expired/failed/cancelled نیز ممکن است برای reconciliation نیاز به حساب قبلی داشته باشند. نگهداری snapshot رمزگذاری‌شده حساب به‌ازای هر پرداخت در این مرحله ساخته نشده؛ جابه‌جایی حساب در استقرار نیازمند رویه رسیدگی است.

## صف پیامک و worker

redirect و درخواست‌های معمول بیمار/ویرایش کارکنان دیگر `dispatch_pending_sms` اجرا نمی‌کنند. رویداد مهم داخل تراکنش اصلی وارد outbox می‌شود؛ worker موجود `python -m app.jobs`، timer هر دقیقه و دو endpoint صریح کارکنان برای اجرای عملیات/ارسال صف از همان dispatcher استفاده می‌کنند. OTP ورود همچنان ارسال مستقیم لازم دارد. این تغییر به BackgroundTasks حافظه‌ای تکیه نمی‌کند.

- کلید dedupe یکتا برای هر hold/event و یادآوری، callback تکراری و انقضا را از ساخت پیامک تکراری بازمی‌دارد. اعلان شکست/انقضای ارسال‌نشده بعد از تأیید پرداخت لغو می‌شود؛ پیامی که قبلاً ارسال شده قابل پس‌گرفتن نیست.
- هر پیام زیر قفل، جداگانه با token و lease دو دقیقه claim و commit می‌شود؛ I/O پیامک بیرون قفل است. worker دیگر پیام در حال ارسال را برنمی‌دارد. نتیجه فقط با token همان claim ثبت می‌شود.
- حداکثر ۳ تلاش، فاصله ۵ سپس ۱۰ دقیقه و ثبت `next_attempt_at` در DB؛ crash/lease منقضی به failed و تأخیر ۵ دقیقه برمی‌گردد. خطای ذخیره‌شده عمومی است و body/credential ارائه‌دهنده را افشا نمی‌کند. وضعیت sending/cancelled در پنل نمایش درست دارد.
- خاموشی عمدی سرویس، صف و بودجه تلاش را حفظ می‌کند. تولید یادآوری نیز زیر قفل و dedupe انجام می‌شود. `TimeoutStartSec=1h` برای jobs با سقف ۲۰۰ پیام قرار گرفت؛ اجراهای systemd یک سرویس هم‌زمان نمی‌شوند و claim، اجرای دستی موازی را هم کنترل می‌کند.
- تحویل پیامک **at-least-once** است: اگر ارائه‌دهنده پیام را پذیرفت و process پیش از ثبت رسید از بین رفت، retry ممکن است تکرار کند. سرویس فعلی کلید idempotency قطعی ندارد؛ ادعای exactly-once ارسال خارجی نداریم. تعداد محدود retry، هشدار وضعیت نامشخص و بررسی گزارش ارائه‌دهنده لازم است. claim فقط تکرار workerهای هم‌زمان سالم را می‌بندد.

## مهاجرت، rollback و آزمون

0017 چهار فیلد outbox و constraint dedupe اضافه می‌کند؛ داده‌های قبلی حفظ می‌شوند. revision مرکزی و اطلاعات مطب هم‌تراز می‌شوند؛ seed نصب تازه نیز revision مهاجرت را می‌گیرد. در rollback، ارسال بدون رسید به failed با attempts=3 می‌رود تا worker قدیمی ناخواسته دوباره نفرستد؛ فیلدهای جدید overlay/history پاک می‌شوند. نسخه قدیمی کلید رزرو ندارد، بنابراین rollback فقط در حالت maintenance و با backup هماهنگ DB/کد/ENV/کلیدها انجام شود؛ downgrade0016 نیز کارکنان و نشست‌ها را غیرفعال می‌کند.

۲۱۵ تست pytest (۳۰ تست تازه این مرحله)، lint/build/نسخه، frozen sync با۴۵بسته، Ruff بحرانی، migration با داده قبلی/rollback/seed/CAS، Nginx HTTP/HTTPS syntax و runtime cookie/CSRF/MFA/WebSocket/headers/404/410/rate و تغییر فوری سیاست رزرو PASS. ممیزی frontend production صفر آسیب‌پذیری شناخته‌شده گزارش کرد؛ ممیزی تازه backend به DNS ابزار خورد و اجرا نشد. dependency تازه به پروژه اضافه نشده است. screenshot موبایل رزرو خاموش روی API/Nginx محلی و فرم تنظیمات با API ساختگی ثبت شد؛ پذیرش واقعی ارائه‌دهندگان و Linuxsystemd باقی است.

سناریوها: پیش‌فرض بسته/API مستقیم، روشن/خاموش و پیام HTML، سیاست تازه زیر قفل، ورود و پرونده و لغو در خاموشی، دو callback هم‌زمان، 100/101/NOK، خطای شبکه و پاسخ دیررس، expiry/free/conflict/refund، ref_id collision و malformed response، صف بدون ارسال در redirect، dedupe و لغو اعلان شکست، claim موازی، backoff/سقف/restart، تعلیق پیامک، reminder هم‌زمان و seed تازه پس از مهاجرت. همه داده‌ها ساختگی و شبکه مالی/پیامک mock بود.

محدودیت‌ها: پذیرش حساب/شبکه واقعی کپچا از مرحله۴، پرداخت و SMS واقعی، مرورگر احرازشده staging و systemd روی Linux باقی‌اند. API/Nginx واقعی فقط localhost با DB جدا آزمایش شد؛ فرم مدیرکل screenshot با API ساختگی است. CI مستقل در GitHub هنوز برای مرحله۹ برنامه‌ریزی شده است. refresh ممیزی backend با pip-audit به DNS دانلود tomli از files.pythonhosted.org خورد؛ ممیزی قبلی مرحله۴ نتیجه تازه محسوب نمی‌شود، dependency پروژه تغییر نکرد. سه هشدار deprecation قدیمی pytest و هشدار قدیمی listen http2 در Nginx باقی‌اند.

مرحله بعد: مرحله۶، مقالات با دسترسی backend، ویرایشگر/رسانه، پاک‌سازی HTML، پیش‌نویس/انتشار و بازخورد سئو؛ مرحله۷ نظرات و سپس مرحله۸ طراحی/صفحات خدمات. نقشه‌راه و AI handoff باید در هر تحویل همراه کد تازه شوند.

## 2026-10-01 — اصلاح نمایش رزرو خاموش، نسخه1.12.1

طبق اصلاح صریح مالک، /appointment/ در حالت خاموش فقط پیام تنظیم‌شده و تقویم متوقف با انیمیشن تنفس آرام دارد؛ فرم ورود و پنل بیمار اصلاً mount نمی‌شوند، حتی با cookie قبلی. CSS عمومی و HTML اولیه بدون JavaScript هم همین پیام را دارند. prefers-reduced-motion انیمیشن را خاموش می‌کند. برچسب صفحه اصلی وضعیت نوبت‌دهی است؛ ادعای دسترسی UI ورود در خاموشی حذف شد. API پرونده و callback پرداخت شروع‌شده برای سازگاری و رسیدگی قبلی حفظ شده‌اند؛ این تصمیم درباره نمایش عمومی است. بررسی تازه سیاست قبل از mount فرم لازم است و شکست API رزرو را بسته نگه می‌دارد. متن سیاست قدیمی حفظ ورود UI در این اسناد، با همین درخواست تازه مالک جایگزین شد.
