# مرحله ۲ — نقش‌ها و کارکنان، نسخه 1.9.0

تاریخ: 2026-09-30، Asia/Tehran. مبنا: main پس از ادغام PR شماره ۱، کامیت `08e929675777682701b9adb411759bb31cd69b2f`. محدوده این تحویل مدیرکل، نقش سفارشی، مجوز واقعی، مدیریت کارکنان و سازگاری پنل فعلی است. مرحله ۳ هنوز آغاز نشده است.

## قابلیت‌ها و سیاست دسترسی

- جداول `roles`، `permissions`، `role_permissions` و `staff_roles`؛ هر کارمند چند نقش دارد و مجوزهای نقش‌های فعال با هم جمع می‌شوند. شناسه مجوز ثابت است؛ نام و توضیح نقش فارسی و قابل تغییر هستند.
- مدیرکل محافظت‌شده؛ مدیر، منشی، حسابدار و نویسنده پیش‌فرض؛ ساخت نقش‌های جدید بدون محدودیت به این نمونه‌ها. نقش سیستم حذف نمی‌شود؛ نقش سفارشی بدون عضو حذف می‌شود و نقش دارای عضو قابل غیرفعال‌سازی است.
- بخش «نقش‌ها و کارکنان» برای ایجاد/ویرایش/غیرفعال‌سازی نقش، انتخاب مجوز گروه‌بندی‌شده، ایجاد حساب، چند نقش، تغییر رمز و غیرفعال‌سازی کارمند. نام کاربری بعد از ساخت ثابت است؛ رمز حداقل ۱۲ نویسه و هیچ‌گاه در پاسخ/تاریخچه بازگردانده نمی‌شود.
- پیش‌نیازها در انتخاب مجوز خودکار انتخاب می‌شوند و حذف پیش‌نیاز، مجوز وابسته را هم از فرم برمی‌دارد. API نیز نبود پیش‌نیاز، مجوز ناشناخته و مجوز ویژه مدیرکل را رد می‌کند.
- `roles.manage`، `staff.manage` و `secrets.manage` فقط به مدیرکل تعلق دارند؛ قابل اعطا به نقش دیگر نیستند. مدیر عادی دیگر مجوز مدیریت حساب‌ها را به‌صرف نام admin ندارد.
- مجوزهای مقاله/رسانه/نظرات و مدیریت اسرار برای مراحل آینده رزرو و با برچسب روشن نشان داده شده‌اند. ذخیره این مجوزها به معنی پیاده‌سازی مقاله، نظرات یا مرکز تنظیمات نیست.
- تمام مسیرهای داده/عملیات کارکنان مجوز مشخص دارند؛ `/staff/me` برای هویت خود حساب است. WebSocket کارکنان به مجوز گفتگو نیاز دارد. رد اتصال حسابدار به گفتگو، نشست مالی مجاز او را باطل نمی‌کند.
- دریافت اطلاعات و منوی پنل تابع مجوز است. حسابدار خودکار پرونده، تصاویر، گفتگو، لیست بیماران یا پیامک را بارگیری نمی‌کند. آمار داشبورد فاقد مجوز از سرور حذف/صفر می‌شود و کارت مربوط در UI نمایش داده نمی‌شود.
- یادداشت پزشکی، شرح‌حال، رضایت‌نامه، تصاویر، گفتگو و اطلاعات مالی پرونده کنترل مستقل دارند. نوبت/اکسل بدون مجوز پرونده یادداشت یا سابقه مراجعه را افشا نمی‌کند. فهرست‌خوان بیمار، برچسب بالینی، پیگیری، شناسه هویتی یا آمار نوبت را از فهرست بدون مجوز مربوط دریافت نمی‌کند.
- اطلاعات حسابداری لازم برای عملیات نوبت در مجوز نوبت باقی است؛ `finance.view` دسترسی به مجموعه گزارش‌ها و پرداخت‌هاست. `audit.view` صریحاً شامل جزئیات حساس تاریخچه است؛ `sms.view` شامل متن و مخاطب پیامک است. مدیرکل باید این موارد را هنگام ساخت نقش در نظر بگیرد.
- لغو نوبت از تأیید/تغییر وضعیت جداست؛ تغییر یادداشت نوبت به مجوز ویرایش پرونده نیاز دارد. درخواست تغییر وضعیت بدون فیلد staff_note، یادداشت قبلی را حفظ می‌کند.
- تغییر نقش/عضویت/رمز/فعال بودن حساب در audit ثبت و نشست‌های مرتبط باطل می‌شوند. fingerprint نیز تغییر مستقیم جداول مجوز را تشخیص می‌دهد. اتصال باز در پیام بعدی، پیش از انتشار رویداد یا در heartbeat قطع می‌شود؛ بررسی فقط هنگام اتصال نیست. پاسخ 401 به درخواست کارکنان، هویت پنل مرورگر را هم پاک می‌کند.
- تغییرات مدیریت با `BEGIN IMMEDIATE` در SQLite سری می‌شوند؛ حذف نقش مدیرکل یا غیرفعال‌سازی/گرفتن نقش آخرین مدیرکل فعال با 409 رد می‌شود، حتی با دو درخواست هم‌زمان. حساب کارمند حذف فیزیکی ندارد؛ غیرفعال می‌شود.

## نصب جدید تأییدشده توسط مالک

مالک «نصب جدید» را انتخاب کرده است. هیچ حساب production و هیچ رمز مالک در این مرحله ساخته یا دریافت نشده است. هنگام راه‌اندازی مجاز، در محیط امن سرور و پوشه api:

```sh
uv run alembic upgrade head
uv run python -m app.setup_owner --username YOUR_OWNER_USERNAME --name "مدیرکل"
```

ابزار رمز را دوبار به‌صورت مخفی می‌پرسد؛ آن را در آرگومان فرمان، ENV نمونه یا چت ننویسید. سپس با حساب انتخابی به `/staff/` وارد شوید. برای نصب جدید ساخت مدیرکل از این ابزار کافی است؛ `BOOTSTRAP_ADMIN_*` را خالی بگذارید. این ENV و ابزار `app.create_admin` همچنان فقط مدیر عادی می‌سازند.

برای ارتقای حساب موجود، فقط با انتخاب صریح نام کاربری از `app.setup_owner --username ... --promote-existing` استفاده شود. هیچ admin قدیمی خودکار مدیرکل نمی‌شود. مدیریت چند مدیرکل از پنل ممکن است؛ آخرین حساب فعال محافظت می‌شود.

## مهاجرت و بازگشت

`20260930_0014` نقش‌های قبلی admin/secretary را به عضویت متناظر منتقل و نشست‌های کارکنان را باطل می‌کند. patient session دست‌نخورده می‌ماند. برنامه نقش‌های جدید را فقط هنگام نبودن می‌سازد؛ ویرایش نقش پیش‌فرض هنگام restart به مقدار اولیه بازنمی‌گردد. سازگاری ایجاد حساب توسط ابزارهای قدیمی در login/seed برقرار است، اما رشته role منبع مجوز نیست.

قبل از مهاجرت واقعی backup و پذیرش staging لازم است. در downgrade، برای جلوگیری از اعطای دسترسی گسترده کد قدیمی، همه حساب‌های کارکنان غیرفعال و نشست‌ها باطل می‌شوند؛ فعال‌سازی دوباره فقط بعد از بررسی صریح دسترسی حساب‌هاست. برگشت DB به‌تنهایی عضویت سفارشی حذف‌شده را بازنمی‌گرداند؛ بازیابی backup معتبر لازم است.

مرورگر پنل حسابدار فقط `staffStats`، `staffFinanceSummary` و `staffPayments` را فراخواند. تست مرورگر از فرم ورود/کپچا عبور نکرد و آزمون اتصال کامل UI به API واقعی کارکنان در staging باقی است؛ آزمون‌های API، نشست cookie، CSRF و WebSocket با TestClient واقعی backend و داده ساختگی اجرا شدند.

سه هشدار pytest از مرحله قبل باقی‌اند (TestClient/httpx و دو نام قدیمی 422). build در نبود API از اطلاعات fallback برای prerender استفاده کرد؛ حل تازه‌ماندن HTML عمومی بعد از تغییر مطب در مرحله ۳ است. هیچ خطای حل‌نشده در آزمون نهایی ثبت نشد؛ خطاهای گذرای fixture/ویرایش JSX اصلاح و checks دوباره اجرا شدند.

هیچ deploy، پیامک/پرداخت واقعی یا فعال‌کردن نوبت‌دهی انجام نشده است. MFA و Google/Cloudflare مرحله ۴ هستند؛ امنیت نقش جای MFA را نمی‌گیرد.
