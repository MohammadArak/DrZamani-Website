# انتشار و بازیابی هماهنگ — نسخه 1.16.0

این راهنما مجوز استقرار نیست. سایت زنده، رزرو، پرداخت، پیامک و حساب واقعی در این مرحله تغییر نکرده‌اند. آزمون‌ها از دیتابیس و فایل‌های ساختگی مستقل استفاده می‌کنند. فرمان‌های systemd، Nginx، runuser و نصب uv روی VPS هنوز پذیرش عملی ندارند.

## ورودی و ترتیب عملیات

اسکریپت‌های root-only فقط با درخواست صریح استقرار استفاده شوند:

```text
deploy/deploy-release.sh /absolute/path/to/built-release.zip
deploy/rollback-release.sh PREVIOUS_RELEASE_ID SUCCESSFUL_DEPLOYMENT_RECEIPT_ID
```

ZIP سورس تحویل، بسته انتشار نیست؛ بسته انتشار باید public_html ساخته‌شده، VERSION، کد API، قفل وابستگی‌ها، migration و دو snippet هدر را داشته باشد و ENV واقعی داخلش نباشد. مسیرهای رسانه خصوصی/عمومی و SQLite باید صریح و زیر /var/lib/drzamani باشند. Python سیستم حداقل 3.11 و Python API طبق قفل پروژه 3.12 است. هویت commit/artifact کامل بسته انتشار هنوز گیت باز مرحله۱۰ است؛ بررسی VERSION به‌تنهایی آن را اثبات نمی‌کند.

انتشار و rollback یک قفل مشترک دارند. maintenance پیش از توقف timer، job در حال اجرا و API فعال می‌شود. توقف ناموفق هیچ migration یا بازیابی را شروع نمی‌کند. قبل از تغییر، SQLite با backup API مستقل از WAL و با integrity/foreign-key check ذخیره می‌شود؛ رسانه عمومی، فایل خصوصی، ENV و snippetهای Nginx همراه آن snapshot می‌شوند. manifest، هش فایل‌ها و رسید با دسترسی خصوصی نگهداری می‌شوند. همه نویسندگان دیگر باید توسط اپراتور شناسایی و متوقف باشند؛ این ابزار تنها سه unit شناخته‌شده را کنترل می‌کند.

کد جدید تنها پس از migration، پاسخ JSON سلامت با VERSION مورد انتظار و بررسی/reload Nginx پذیرفته می‌شود. timer از قبل خاموش، روشن نمی‌شود. خطای migration/سلامت/Nginx/شروع jobs موجب تلاش برای بازگرداندن کد، دیتابیس، رسانه و تنظیمات پیش از عملیات می‌شود. اگر بازیابی شکست بخورد maintenance باقی می‌ماند و توقف مجدد نویسندگان تلاش می‌شود؛ نتیجه واقعی هر unit باید بررسی شود.

فرمان‌های زیرساختی در گروه پردازشی مستقل اجرا می‌شوند؛ هنگام timeout یا interrupt، گروه متوقف و خروج آن انتظار کشیده می‌شود تا فرزند فرمان در زمان restore ننویسد. این مسیر با نویسنده فرزند ساختگی در Linux آزموده می‌شود؛ رفتار واقعی runuser/systemd همچنان گیت عملی مستقل است. خواندن تنظیمات با Python نسخه سرویس نیز تحت www-data انجام می‌شود، چون اجرای محیط تحت مالکیت سرویس با root مجاز نیست.

rollback به رسید انتشار موفق متناظر نیاز دارد و snapshot همان کد قبلی را بازیابی می‌کند؛ صرفاً کد را عوض نمی‌کند و alembic downgrade اجرا نمی‌کند. **ویرایش‌ها و بارگذاری‌های بعد از آن snapshot از وضعیت فعال خارج می‌شوند.** ابتدا snapshot پیش از rollback گرفته می‌شود و نسخه‌های کنارگذاشته‌شده خصوصی حفظ می‌شوند. انتخاب زمان بازگشت و بازیابی تغییرات جدید تصمیم اپراتور است.

## خرابی ناگهانی و نگهداری

هر resource با rename روی همان filesystem جایگزین می‌شود؛ کل مجموعه یک تراکنش filesystem نیست. توقف اجباری فرآیند یا قطع برق ممکن است وضعیت میانی ایجاد کند. journal خصوصی prepared/restored در backup و پوشه‌های .restore-stage-* کنار resource باقی می‌مانند. بعد از چنین خرابی maintenance را کورکورانه حذف نکنید و سرویس‌ها را شروع نکنید: همه نویسندگان را متوقف نگه دارید، journal، current، فایل‌های previous و manifest/هش معتبر را بررسی و وضعیت هماهنگ را بازیابی کنید. بازیابی خودکار پس از SIGKILL/قطع برق پیاده‌سازی یا آزموده نشده است.

backup و ENV رمزنگاری داخلی ندارند؛ دسترسی root-only، ذخیره خارج webroot، رمزنگاری مقصد خارج سرور، انتقال امن و سیاست نگهداری/حذف مورد نیازند. پوشه‌های incomplete، journal و وضعیت‌های کنارگذاشته‌شده خودکار حذف نمی‌شوند. رسید /var/backups/drzamani/ID.json و snapshot متناظر را با هم نگهدارید؛ هش manifest باید از رسید معتبر بیاید. تغییر محتوا، مسیر، فایل اضافه/ناقص یا symlink پیش از restore رد می‌شود.

## پذیرش

templateهای همراه، تمام مسیرهای proxy از جمله مقالات و sitemap را در maintenance می‌بندند؛ GET آن‌ها ممکن است انتشار زمان‌بندی‌شده بنویسد. **این مدیر انتشار template سایت فعال را نصب نمی‌کند.** اپراتور باید پیش از rollout، guardها را در تنظیم فعال Nginx تأیید کند. آزمون template اصلاح‌شده جای بررسی تنظیم فعلی VPS نیست.

آزمون‌های Windows شامل SQLite/WAL، integrity، hash، فایل‌های ناقص، ZIP نامعتبر و خطای rename هستند. آزمون‌های Linux additionally از filesystem، symlink، قفل و دیتابیس واقعی موقت استفاده می‌کنند ولی adapter سرویس‌ها ساختگی است. موفقیت این آزمون‌ها برابر با پذیرش VPS/systemd/Nginx واقعی، provider یا production نیست. وضعیت اجرای دقیق در docs/PHASE_10_RECOVERY.md ثبت می‌شود.
